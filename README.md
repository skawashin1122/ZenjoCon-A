## 0. なぜ大きく方針を変えたのか（v2 → v3）

v2（AI音声トリアージ中心）を「高校生が約5週間で作り、実際の人に使ってもらい、効果を確かめられるか」という基準で見直した結果、次の問題があった。

| v2の問題 | 理由 | v3での対応 |
|---|---|---|
| **AIで緊急度を判定する** | 医師法・薬機法の境界にあり、判定ミスは命に関わる。高校生が安全性を証明できない。実際の急病で試すことも不可能 | **判定はしない**。「迷ったら」は国の公式ツール（Q助）・119・電話相談へ案内するだけ |
| **既存サービスと重複** | 消防庁の「Q助」が既に同じ役割を持つ | 既存サービスと**競合しない**領域（毎日の見守り・情報の備え）に集中 |
| **健康情報をサーバー・AIに送る** | 病歴・服薬は「要配慮個人情報」。高校生のサーバーで管理するのはリスクが大きい | **健康情報はサーバーに一切保存しない**（端末内で作って印刷するだけ） |
| **24時間動くサーバーが必要** | AWS Academy の Learner Lab は約4時間で EC2 が停止する | 常時稼働が必要な部分を最小化し、実証期間の運用方法を明記（4-4） |
| **効果を測れない** | 「救急出動を減らす」はアプリで証明できない | **実証実験で測れる指標**（応答率・家族への通知の正しさ・カードの読み取り時間）に変更 |
| **協力者（民生委員・消防団）が前提** | 5週間で地域の協力体制は作れない | 実証は**家族のみ**で行い、地域協力者は「最終審査会までの発展」に位置づけ |

> **v3の基本方針**：「AIに命の判断をさせない」「健康情報を預からない」「5週間で動くものを作り、実際に使ってもらって数字で振り返る」

### 1-2. データを扱う上で気づいた注意点（情報Ⅰ「データの扱い」）

1. **冊子によって集計期間がバラバラ**：消防は暦年、社会・自然動態は年度、保健衛生は12/31や10/1時点。→ 冊子の発行年ではなく**調査時点で並べ直した**。
2. **同じ数値の使い回し**：R7版とR8版の保健衛生（R5.10.1）、R6〜R8版の医療従事者数（R4.12.31）は同じ。
3. **矛盾するデータ**：R5版の保健衛生は「R2.10.1・診療所40」だが、前年のR4版は「R3.12.31・診療所50」。→ 元の調査（県の医療施設調査）で確認が必要。
4. **推計値と確定値の混在**：R8版の地区別人口はR2国勢調査をもとにした推計値、R7国勢調査は速報値。
5. **比較するときは割合に直す**：人口が変わっているので、件数ではなく**人口千人あたり**で比較した。

### 1-3. 課題の定義

ミニ統計から「高齢化」「単身化」「救急需要の増加」「災害リスク」が同時に進んでいることがわかる。これを、**高校生がアプリで手を出せる大きさ**の課題に絞り込んだ。

> **課題A「気づかれない空白」**：一人暮らしの高齢者が家で倒れても、**誰も気づかないまま時間が過ぎる**。人の少ない中山間地ほど起こりやすい。
>
> **課題B「伝わらない空白」**：救急や災害のとき、本人が話せないと、**持病・薬・家族の連絡先が救急隊や避難所に伝わらない**。家族も離れて住んでいる。

**あえてやらないこと**：症状から緊急度を判定すること（119番・**日南市救急医療電話相談（医師・看護師が対応）**・国の「Q助」の役割。アプリからは案内するだけ）。救急出動件数を減らすこと（アプリの効果として証明できないため、目標にしない）。

## 2. 解決策の全体像

### 2-1. コンセプト：フェーズフリー見守り

「フェーズフリー」とは、**普段使っているものが、そのまま非常時にも役立つ**という考え方。非常時のためだけのアプリは、いざという時に使い方を忘れていて役に立たない。

```text
 【平常時】                         【もしもの時】
 毎朝「げんき」ボタンを1タップ   →   押されない日 → 家族にすぐ通知（課題A）
 冷蔵庫に「もしもカード」        →   救急隊・避難所に情報が伝わる（課題B）
 家族とLINEでつながっている      →   大きな地震の直後に自動で安否確認（課題A・B）
```

### 2-2. 3つの機能

| 機能 | 内容 | 解決する課題 | 優先度 |
|---|---|---|---|
| **① げんきボタン** | LINEのメニューの大きなボタンを毎朝1回押すだけ。決めた時刻までに押されないと、再通知→家族に通知 | A | ★★★（必須） |
| **② もしもカード** | 持病・薬の保管場所・かかりつけ医・家族の連絡先・避難先をスマホで入力し、**大きな文字の紙**に印刷して冷蔵庫と非常袋へ。**健康情報はサーバーに保存しない** | B | ★★★（必須） |
| **③ 地震の自動安否確認** | 気象庁のデータで**日南市に震度5弱以上**を検知すると、登録者全員に「無事？」ボタンを自動送信し、結果を家族に通知 | A・B | ★★（応募までに試作） |
| ④ データで見る日南（探究の成果） | ミニ統計5年分のグラフ。調査時点・出典つき | 説明・啓発 | ★ |

**使う人**
- **本人**：一人暮らし（または高齢夫婦のみ）で、LINEを使っている高齢者
- **家族**：離れて暮らす子・孫（通知を受け取る）
- **救急隊・避難所の人**：紙のカードを読むだけ（アプリ不要）

### 2-3. ペルソナと利用シーン

**Aさん（82歳・酒谷・一人暮らし）と、宮崎市に住む子のBさん**

| 時刻 | できごと | まもりネットの動き |
|---|---|---|
| 毎朝7:30 | Aさんが起きてLINEの「げんき」を押す | 「おはようございます。今日もげんきやね！」と返信。Bさんには何も通知しない（毎日通知すると見なくなるため） |
| ある朝10:00 | Aさんが台所で転倒し、動けない | 「げんき」がまだ押されていないので、Aさんに再通知 |
| 11:00 | 応答なし | **Bさんに通知**「お母さんの『げんき』がまだです。電話してみてください」＋電話ボタン |
| 11:05 | Bさんが電話→出ない→近所の親戚に見に行ってもらう→119番 | 救急隊は冷蔵庫の**もしもカード**で持病・薬・Bさんの連絡先をすぐ確認 |

> まもりネットがない場合、Aさんは**翌日以降まで誰にも気づかれない**かもしれなかった。

### 2-4. 既存サービスとの違い

| 既存サービス | 課題 | まもりネットとの関係 |
|---|---|---|
| 市の緊急通報装置（設置型） | 機器の設置が必要。倒れて押せないと使えない | まもりネットは「**押さないこと**」で異変を知る。併用できる |
| 郵便局などの見守り訪問（有料） | 月額費用、毎日ではない | 毎日・無料。併用できる |
| NPO等の無料LINE見守り（例：NPO法人エンリッチ） | 全国向けで、地域の災害情報や救急の備えとは連携していない | **日南市の地震情報との連動**、**もしもカード**、地区データの活用が違い |
| 救急医療情報キット（紙） | **日南市では配布の情報がない**。他市町村でも手書きで更新されにくい | もしもカードが**市にない「紙で伝える仕組み」を補う**。スマホで入力・印刷し、変更があればすぐ作り直せる |
| マイナ救急（**日南市消防本部が2025年4月以降に実証開始**） | カードの持参が必要、家族の連絡先や生活の情報は載らない | カードに「**マイナ保険証の保管場所**」「家族の連絡先」を書き、補い合う |
| **日南市救急医療電話相談**（0987-31-1111・24時間365日） | 医師・看護師が助言してくれるが、**番号を覚えていないと使えない** | 「迷ったら」ボタンから**ワンタップで電話**できるようにする |
| Q助（消防庁）／#7119（宮崎県は2027年度中の導入を検討中） | 症状の判定・相談 | **判定はこれらに任せる**。#7119は導入後にメニューへ追加 |

## 3. 機能の詳細設計

### 機能①：げんきボタン

**画面**：LINEのトーク画面の下に、画面の半分を使う大きなメニュー（リッチメニュー）を表示。

```text
┌─────────────────────────┐
│                         │
│      🌞 げんき！         │  ← 毎朝これを押すだけ
│                         │
├────────────┬────────────┤
│ 📞 家族に   │ 🚑 迷ったら │  ← 家族に電話／「迷ったら」の案内
│   電話     │            │
└────────────┴────────────┘
```

**「迷ったら」を押したときの画面**（アプリは判定せず、相談先へつなぐだけ）

```text
┌──────────────────────────────────┐
│ 🔴 意識がない・息が苦しい・胸が痛い    │
│    → 【119番に電話】                  │
├──────────────────────────────────┤
│ 🟡 救急車を呼ぶか迷う・夜間や休日     │
│    → 【日南市救急医療電話相談】         │
│       0987-31-1111（24時間365日）     │
│       医師・看護師が答えてくれます      │
├──────────────────────────────────┤
│ ⚪ 自分で調べたい → 【Q助（消防庁）】  │
└──────────────────────────────────┘
 ※このサービスは医療の判断をしません。迷ったら119番へ。
```

- 番号を覚えていなくても**ワンタップで電話**できる（LINEのボタンから電話アプリを開く）。
- 🔴の例は、119番を案内するための**一般的な目安の表示**で、アプリが入力を判定するものではない。表示する文言は消防本部・市の案内に合わせて確認する。
- 宮崎県で#7119が導入されたら（2027年度中の予定で検討中）、市の窓口と合わせて案内する。

**見守りの流れ（状態遷移）**：時刻は本人・家族が設定する（下は例）

```text
           「げんき」を押す
 [待機中] ───────────────────────▶ [げんき] ──(翌日0時)──▶ [待機中]
    │ 10:00 までに押されない
    ▼
 [再通知済み]  本人に「げんきですか？」をもう一度送る
    │ 11:00 までに押されない          │ 押された → [げんき]
    ▼
 [家族に通知済み]  家族に「まだ押されていません」＋電話ボタン
    │ 家族が「確認できた」を押す → [確認済み]
    │ 13:00 になっても家族の確認なし
    ▼
 [第2連絡先に通知済み]  2人目の家族に通知
```

| 状態 | 次の状態へ進む条件 | そのときの動き |
|---|---|---|
| 待機中 | 本人が押す | げんき（返信のみ・家族への通知なし） |
| 待機中 | 再通知時刻を過ぎる | 本人に再通知 |
| 再通知済み | 家族通知時刻を過ぎる | 第1連絡先に通知 |
| 家族に通知済み | 家族が「確認できた」 | 確認済み（記録のみ） |
| 家族に通知済み | 第2通知時刻を過ぎる | 第2連絡先に通知 |

**工夫**
- **通数（コスト）の節約**：LINEの「応答メッセージ」（ユーザーが押したことへの返信）は**無料プランの通数に数えられない**。毎朝の「げんき」は本人が押す→返信する形なので、**毎日の見守りに費用がかからない**。通数を使うのは「再通知」「家族への通知」などの異常時だけ。
  - 試算：利用者1人あたり、異常時の通知は月に数通程度の見込み。無料プラン（月200通）の範囲で、実証実験（5世帯程度）は十分に運用できる。※料金は変わることがあるため、公式の料金ページで確認する
- **「誤報」を減らす工夫**：旅行・入院などで押せない日は、家族が「お休み」を設定できる。実証実験で誤報の件数を数え、時刻の設定を見直す。
- **ひとこと機能（★発展）**：「げんき」と一緒に「きつい」「転んだ」などを送ると、家族への通知の優先度を上げる（キーワードで判定。**優先度を上げることはあっても下げることはしない**）。

- 「最終更新日」を印刷し、**半年ごとにLINEで見直しを呼びかける**。

### 4-2. 技術選択の理由

| 選択 | 理由 | 比べた案 |
|---|---|---|
| **LINE** | 高齢者が普段から使っている。新しいアプリを覚えなくてよい。応答メッセージは無料 | 独自アプリ（インストール・操作の説明が必要）、電話の自動音声（費用がかかる） |
| **もしもカードはブラウザだけで処理** | 健康情報をサーバーに置かないので漏えいしない。サーバーが止まっていても使える | サーバーに保存（便利だが、高校生が要配慮個人情報を管理することになる） |
| **紙に印刷** | 救急隊・避難所の人が、機器なしで確実に読める。停電でも使える | QRコードだけ（読み取り機器が必要） |
| **FastAPI＋SQLite** | Pythonで書け、学習しやすい。小規模なのでデータベースは1ファイルで十分 | PostgreSQL（v2。今回の規模には大きすぎる） |
| **生成AIを使わない（コア機能）** | 命に関わる判断をAIに任せない。説明できる仕組み（状態遷移・ルール）で作る | AIの判定（v2。安全性を証明できない） |
| **気象庁XML** | 公式・無料・リアルタイム。市町村ごとの震度がわかる | 他社の地震API（利用条件・費用の確認が必要） |

### 4-4. 運用上の制約と対策（最大のリスク）

**AWS Academy の Learner Lab は、セッション（約4時間）が終わると EC2 が停止し、再起動のたびにIPアドレスが変わる。** 見守りは毎日動き続ける必要があるため、次のように分けて考える。

| 用途 | 環境 | 備考 |
|---|---|---|
| 開発・テスト・審査のデモ | AWS Academy（EC2・Ubuntu 26.04） | 課題の要件どおり |
| **実証実験（約10日間・常時稼働）** | **要相談**（下の案から選ぶ） | 停止中に押された「げんき」は受け取れないため |

| 実証期間の案 | 良い点 | 注意点 |
|---|---|---|
| ① 学校・先生が用意する常時稼働のサーバー（AWS通常アカウント等） | 同じプログラムがそのまま動く | 費用・学校の許可。**先生に相談** |
| ② 毎朝の見守り時間帯（例 6:00〜10:00）だけ Learner Lab を起動 | 追加費用なし | 起動を忘れると止まる。その時間帯以外のげんき・地震は受け取れない。**実証の制約として正直に記録する** |

また、LINEのWebhookはHTTPS（正式な証明書）が必要。IPアドレスが変わる問題には、Elastic IP の利用可否を確認するか、IPアドレスから名前を作るサービス（sslip.io など）＋Let's Encrypt を使う。

### 4-5. プログラムの要点

**見守りの状態遷移（時刻と状態だけで次の動きを決める関数。テストしやすいよう、LINEやデータベースから切り離して作る）**

```python
from dataclasses import dataclass
from datetime import time
from enum import Enum

class State(Enum):
    WAITING = "待機中"
    GENKI = "げんき"
    REMINDED = "再通知済み"
    FAMILY1 = "家族に通知済み"
    CONFIRMED = "確認済み"
    FAMILY2 = "第2連絡先に通知済み"

class Action(Enum):
    NONE = "何もしない"
    REMIND_SELF = "本人に再通知"
    NOTIFY_FAMILY1 = "第1連絡先に通知"
    NOTIFY_FAMILY2 = "第2連絡先に通知"

@dataclass
class Schedule:
    remind: time = time(10, 0)
    family1: time = time(11, 0)
    family2: time = time(13, 0)

def next_step(state: State, now: time, s: Schedule, on_holiday: bool = False) -> tuple[State, Action]:
    """5分ごとに呼ばれ、次の状態と送るべき通知を返す"""
    if on_holiday or state in (State.GENKI, State.CONFIRMED, State.FAMILY2):
        return state, Action.NONE
    if state == State.WAITING and now >= s.remind:
        return State.REMINDED, Action.REMIND_SELF
    if state == State.REMINDED and now >= s.family1:
        return State.FAMILY1, Action.NOTIFY_FAMILY1
    if state == State.FAMILY1 and now >= s.family2:
        return State.FAMILY2, Action.NOTIFY_FAMILY2
    return state, Action.NONE
```

**地震の判定（気象庁XMLから日南市の震度を取り出す）**

```python
import xml.etree.ElementTree as ET

NICHINAN_CODE = "4520400"   # 気象庁の市町村コード（7桁）。コード表で要確認
NS = {"seis": "http://xml.kishou.go.jp/jmaxml1/body/seismology1/"}
ORDER = ["1", "2", "3", "4", "5-", "5+", "6-", "6+", "7"]   # 震度の順番

def nichinan_intensity(xml_text: str) -> str | None:
    """「震源・震度に関する情報」から日南市の震度を返す（観測なしは None）"""
    root = ET.fromstring(xml_text)
    for city in root.iterfind(".//seis:City", NS):
        if city.findtext("seis:Code", namespaces=NS) == NICHINAN_CODE:
            return city.findtext("seis:MaxInt", namespaces=NS)
    return None

def should_alert(intensity: str | None, threshold: str = "5-") -> bool:
    return intensity in ORDER and ORDER.index(intensity) >= ORDER.index(threshold)
```

## 5. 倫理的配慮・法令・セキュリティ

| 観点 | リスク | 対策 |
|---|---|---|
| **医療** | 医療の判断をしていると誤解される | 症状の判定は一切しない。「迷ったら」は119番・日南市救急医療電話相談・Q助への案内のみ。画面に「このサービスは医療の判断をしません」と表示 |
| **要配慮個人情報** | 病歴・服薬の漏えい | **サーバーに保存しない**（もしもカードは端末内で処理）。サーバーにあるのはLINEのID・呼び名・押した時刻だけ |
| **同意** | 本人が知らないうちに見守られる | 本人と家族の両方から**書面で同意**をもらう（実証実験の同意書を作る）。いつでも登録を解除できる |
| **見守られる側の気持ち** | 「監視されている」と感じる | 毎日の記録を家族に送らない（**異常時だけ**通知）。時刻・お休みを本人が決められる |
| **過信** | 「アプリがあるから安心」と考え、他の備えをしなくなる | 「1日1回の確認で、すぐに気づける仕組みではない」と説明書に明記。市の緊急通報装置などとの併用を勧める |
| **誤報・通知の見逃し** | 家族が通知に慣れて無視する | 実証実験で誤報の件数を数えて改善。平常時は家族に通知しない |
| **デジタル格差** | LINEを使えない人が使えない | もしもカードは家族が代わりに作れる。LINEを使えない人への方法（電話など）は今後の課題として明記 |
| **セキュリティ** | なりすまし・不正アクセス | LINEの署名検証（X-Line-Signature）、HTTPS、サーバーへのログインは鍵認証のみ、アクセス元の制限、S3のバックアップは暗号化 |
| **研究倫理** | 高校生が高齢者のデータを扱う | 実証の協力者は**家族・親戚**から募る。学校（先生）の許可を得る。終了後はデータを削除 |
| **著作権・ライセンス** | 他者の権利の侵害 | 使ったライブラリのライセンス（MIT・Apache等）の一覧、気象庁データの出典表記、ミニ統計の出典表記、アイコン素材の利用規約を確認 |

## 8. 期待される効果と限界

**効果**
1. **異変に早く気づける**：一人暮らしの高齢者が倒れても、遅くとも**その日の昼までに家族が気づける**（設定時刻による）。
2. **救急・災害時に情報が伝わる**：本人が話せなくても、もしもカードで持病・薬・家族の連絡先が救急隊や避難所に伝わる。
3. **地震のあとの安否確認**：日向灘地震や南海トラフ地震のとき、離れて住む家族がすぐに無事を確認できる。
4. **市の相談窓口につながる**：日南市救急医療電話相談（24時間365日）の番号を覚えていなくても、LINEからワンタップで電話できる。軽症の時間外受診が集まる二次救急病院の負担軽減という市の方針を後押しする（※件数への効果は本アプリでは測定できない）。
5. **低コスト**：LINEの応答メッセージと紙を使うので、日々の費用がほぼかからない。財政が厳しい日南市でも続けやすい。
5. **他の地域でも使える**：市町村コードを変えるだけで、全国の中山間地域で使える。

**限界（正直に書く）**
- 1日1回の確認なので、**倒れてすぐに気づけるわけではない**（数時間はかかる）。
- LINEを使わない高齢者は「げんきボタン」を使えない。
- 救急出動件数を減らす効果は、このアプリでは確かめられない。
- 実証実験は小規模（3〜5世帯）で、結果を市全体に当てはめることはできない。
